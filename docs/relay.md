# Собственный relay для Brain ED (E7.7)

Компания может поднять relay на своём доступном из интернета Linux-узле.
Координатор за NAT и клиенты открывают к нему **исходящие TCP-соединения**.
Проброс порта к координатору и VPN для этого маршрута не нужны. Прямой TLS
остаётся доступным независимо от relay. Это предварительная реализация;
процессные проверки ниже выполнены на loopback одной машины, а не в публичной сети.

## Два независимых TLS-слоя

```text
клиент -- TLS relay CA --> relay <-- TLS relay CA -- координатор за NAT
       [      внутри: TLS координатора, его CA, SAN/SNI и Host       ]
```

Внешний TLS защищает отдельные relay-токены от перехвата в публичной сети.
Relay завершает **только внешний TLS** и пересылает вложенные TLS-байты.
Ключа координатора и его прикладного токена у relay нет. Клиент проверяет
прежний CA координатора и его имя; имя регистрации на relay не заменяет SAN.
HTTP Host, роли, пространства и выдача явно опубликованных фактов проверяются
координатором прежним обработчиком. Relay не даёт доступ к приватному архиву.

Нужны **два доверенных CA**: `--ca` координатора и `--relay-ca` посредника.
Системные корни не подключаются. Обе копии CA и join-пакет передают по доверенному
каналу. Подменив сам пакет с CA, атакующий меняет доверие клиента: relay этого
не предотвращает. Скомпрометированный relay может оборвать/задержать поток и
видит адреса участников, имя маршрута, время, объём трафика и метаданные
вложенного TLS-рукопожатия (например SNI). Содержимое запросов и ответов
остаётся за TLS координатора.

## 1. Подготовить публичный узел

Примеры — команды настройки, не стенограмма публичного развёртывания.
`relay.example.test` замените на доступный DNS/IP своего узла. Для теста на
одной машине используйте `localhost` и `127.0.0.1:7444`. Все каталоги и файлы
задаются явно; отдельный пользователь ОС запускает сервис без sudo.

```sh
brain net init --state-dir ./relay-state --name relay.example.test
brain net relay token add --state-dir ./relay-state \
  --name office-coord --role register --token-out ./office-register.token
brain net relay token add --state-dir ./relay-state \
  --name office-coord --role connect --token-out ./alice-connect.token
brain net relay serve --listen 0.0.0.0 --port 7444 --state-dir ./relay-state
```

Последняя команда работает, пока stdin открыт. Supervisor должен держать его
открытым; закрытие stdin останавливает listener, закрывает сокеты и дожидается
потоков. `--port 0` выдаёт свободный порт в первой JSON-строке `bind`.
Открыть входящий TCP-порт нужно только на relay. `net init` создаёт его
сертификат и ключ в `relay-state/tls`; CA координатора создаётся отдельно.

Токены relay живут в **отдельном** `relay-state/relay-auth/auth.sqlite`.
Используется существующее хранилище AuthStore: 256 случайных бит, BLAKE3-хеш
секрета, сравнение за постоянное время, файлы БД/WAL/SHM 0600, каталог 0700.
Существующие небезопасные права на БД/каталог и symlink отклоняются.
Токен пишется только в новый файл 0600; stdout содержит лишь `token_id`.
Зависимостей для E7.7 не добавлено: используются существующие rustls, serde,
BLAKE3, SQLite и стандартная библиотека.

Каждый токен привязан к **одному имени** `[a-z0-9-]{3,64}` и роли:

- `register` выдаётся только владельцу координатора;
- `connect` выдаётся каждому клиенту отдельно, в том числе для join-пакета.

Клиентский токен не может зарегистрировать координатор, а токен другого имени
не может занять `office-coord`. Несколько register-токенов одного имени —
полномочие администратора relay; такие координаторы разделят очередь имени.
TLS координатора всё равно проверяется независимо. Срок токена — 90 дней.
Для ротации выдают новый токен, распространяют его и отзывают прежний:

```sh
brain net relay token revoke --state-dir ./relay-state --token-id TOKEN_ID
```

Очередь и активные туннели перепроверяют отзыв с интервалом 100 мс (плюс время
операций I/O/SQLite). Координатор загружает свой токен при запуске; при замене
файла его нужно перезапустить. Токен координатора `net revoke` и relay-токен
отзываются независимо.

## 2. Поднять координатор за NAT

Передайте ему `office-register.token` и `relay-state/tls/ca.pem` через доверенный
канал. Отдельно инициализируйте собственный CA координатора:

```sh
brain net init --state-dir ./coord-state --name coord.example.test
brain net serve --state-dir ./coord-state --listen 127.0.0.1 --port 7443 \
  --via-relay relay.example.test:7444 --relay-name office-coord \
  --relay-token-file ./office-register.token --relay-ca ./relay-ca.pem
```

`--relay-server-name NAME` задаёт проверяемый SAN/SNI relay, если dial использует
IP или алиас. По умолчанию это host из `--via-relay`. Он **не** является именем
сертификата координатора. DNS разрешается только для явно заданного адреса
relay, при подготовке конфигурации; SNI координатора никогда не резолвится.
Прямые IP-адреса координатора сохраняют прежние LAN/CGNAT opt-in правила.

Координатор с `--via-relay` слушает loopback. Четыре исходящих слота регистрируют
имя и ждут клиентов. После спаривания слот копирует вложенный TLS к собственному
loopback TLS-listener. Обрыв или недоступный relay вызывают переподключение с
backoff 100 мс → максимум 5 с. Нет автоматического повтора прикладной операции.
`status: serving` подтверждает локальный listener, а не успешную регистрацию;
её проверяют клиентским `net status`. После смены DNS-адреса relay процесс
перезапускают: адрес разрешается один раз при настройке маршрута.

## 3. Выдать пакет или подключить клиента явно

На машине координатора подготовьте connect-токен клиента и CA relay:

```sh
brain net enroll --state-dir ./coord-state \
  --machine alice-laptop --agent-id codex --role worker --grant-space team.demo \
  --credential-out ./alice.credential --bundle-out ./alice.bundle \
  --via-relay relay.example.test:7444 --relay-name office-coord \
  --relay-token-file ./alice-connect.token --relay-ca ./relay-ca.pem
```

Здесь **нет `--dial` координатора**: клиенту достаточно relay. Можно добавить
`--dial IP:PORT` для прямого маршрута с relay как запасным.

Пакет без relay остаётся **v1**. Пакет с relay — **v2**: добавлен объект `relay`
(`address`, `name`, `server_name`, `ca_pem`, `credential`), список `dial` может
быть пустым. Новый клиент читает v1 и v2. Старый клиент явно отказывает на v2;
поэтому расширение не добавлено необязательным полем v1, которое старый клиент
мог бы проигнорировать. Пакет содержит два разных секрета и должен оставаться
0600. Relay никогда не получает прикладной токен из него.

На клиенте:

```sh
brain net join ./alice.bundle --state-dir ./client-state --consume
# Для автоматических настроек используйте стандартный каталог net/client
# выбранного изолированного BRAIN_HOME, либо передайте пути явно:
brain net status --server-name coord.example.test \
  --ca ./client-state/ca.pem --credential ./client-state/credential.pem \
  --via-relay relay.example.test:7444 --relay-name office-coord \
  --relay-token-file ./client-state/relay-token --relay-ca ./client-state/relay-ca.pem
```

Если `net join` выполнен без `--state-dir`, `net status` и `net call` читают
настройки из `$BRAIN_HOME/net/client/endpoint.json` без дополнительных флагов.
Join раскладывает relay CA и токен в отдельные файлы 0600; в endpoint.json
остаются ссылки на них. `--consume` удаляет исходный пакет после успешного join.

При наличии прямого адреса клиент сначала пробует TCP к нему, расходуя до трети
общего дедлайна на connect. При отказе/таймауте **TCP connect** оставшийся
бюджет используется для relay. Ошибка TLS, отказ координатора или неизвестный
исход записи не переключают маршрут и не повторяют запрос. Дедлайн остаётся
общим для connect, внешнего TLS, внутреннего TLS и ответа; разрешение DNS при
подготовке конфигурации зависит от системного resolver и в него не входит.

## Командные вопросы

`team peer` принимает те же relay-флаги. Для каждого источника руководитель
закрепляет прежние origin/project/space, CA, SNI и прикладной reader credential:

```sh
brain team peer --machine worker-one --origin ORIGIN --project checkout \
  --team-space team.checkout --server-name coord.example.test \
  --ca ./worker-ca.pem --credential ./leader-reader.credential \
  --via-relay relay.example.test:7444 --relay-name office-coord \
  --relay-token-file ./leader-connect.token --relay-ca ./relay-ca.pem
brain team ask 'Какие ошибки сейчас открыты?' --machines worker-one
```

Явное согласие источника, grant получателю, публикация и проверка полного
среза обязательны, как при прямом TLS. Сбой relay не превращается в ответ из
старого кэша. Сохранённые ранее peer-конфигурации без relay продолжают читаться. Настройки
маршрута peer всегда явные: они не наследуют relay из постороннего `net join`
на машине руководителя.

## Ограничения и эксплуатация

По умолчанию:

| Ограничение | Значение | Флаг |
|---|---:|---|
| Все открытые сокеты, включая неаутентифицированные и ожидающие | 128 | `--max-connections` (2–1024) |
| Ожидающие регистрации одного имени | 4 | фиксировано |
| Скорость одного туннеля, сумма двух направлений | 4 MiB/s | `--bytes-per-second` (1024–1 GiB/s) |
| Простой регистрации/туннеля | 30 с | `--idle-secs` (1–300) |
| Абсолютная жизнь спаренного туннеля | 300 с | `--max-session-secs` (idle–3600) |
| Внешний TLS + регистрационный заголовок | 3 с | фиксировано |
| Заголовок регистрации | 2048 байт | фиксировано |

Один туннель занимает два учитываемых сокета. У координатора четыре исходящих
слота, поэтому одновременно через relay обслуживаются максимум четыре его
запроса. Копирование использует два буфера по 16 KiB и ограниченные буферы
rustls с backpressure. Скорость ограничивается окнами в одну секунду; частичные
записи могут добавить до 32 KiB всплеска. Это ограничение payload, без накладных
TLS-заголовков. Общий потолок полосы получается из числа туннелей и их лимита;
отдельной глобальной квоты полосы и квот по IP нет. Ресурсы ОС, firewall и
ограничение входящего сетевого трафика остаются задачей оператора.

Relay сохраняет только учётные записи, хеши и служебные поля времени/отзыва.
Содержимое потоков на диск не пишется. stderr — фиксированное JSON-событие
`relay_connection` с категорией `closed` или `refused_or_closed`, без имён,
токенов и тела. Ротацию и срок хранения этого журнала задаёт supervisor.
При закрытии stdin все соединения отменяются, потоки дожидаются завершения.

## Воспроизводимые проверки

```sh
CARGO_TARGET_DIR=/path/to/target cargo build --locked -p brain-cli
BRAIN_PROBE_BIN=/path/to/target/debug/brain python3 -B -m unittest -v tests.test_relay
BRAIN_DEMO_BIN=/path/to/target/debug/brain tools/team-demo.sh --via-relay --machines 2
```

Тест запускает реальные relay/координатор/CLI-процессы на 127.0.0.1 и отдельные
временные HOME. Проверяет relay-only `net status`, `net call`, bundle v2/join,
прямой TCP fallback, чужой токен, неверную роль, подмену имени, отзыв активного
туннеля, лимит неаутентифицированных сокетов, таймауты и перезапуск relay.
Подставной координатор с собственным сертификатом отвергается клиентом,
закреплённым на CA настоящего координатора; неправильный SAN также отвергается.
Демо проверяет `team ask`, отключение класса фактов и отказ выдавать старый
срез при offline. Rust-регрессии проверяют rate limit, частичные записи,
half-close, предел жизни/простоя и освобождение слотов.

Не реализованы: P2P, Iroh, QUIC/UDP, hole punching/STUN/TURN, автоматический
выбор relay, публичная служба Brain, mesh/fleet discovery, кластер/HA relay,
автоматическое получение сертификатов и ротация токенов, квоты по IP,
ресюмирование потоков и повтор неизвестных исходов. Проверки на реальном NAT,
публичном сервере, длительная нагрузка и платформы кроме Linux ещё нужны.
